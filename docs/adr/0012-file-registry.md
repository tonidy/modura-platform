# ADR-0012: File registry, release history in git

Status: Accepted (M8).

## Context

The Contract Registry from ADR-0008 is a service. That suits a team that already runs one, and it is the only setup where nobody can skip the compatibility rules. But a lot of projects want a release history and no extra service to run, back up and secure. The question that started M8 was whether the registry could be a SQLite file committed to the repository.

## Decision

The registry gets a second backend: a folder of release files committed to git. The same commands work against either one, chosen by the target: `--registry http(s)://...` for the server, `--registry file:<dir>` for files, with a default in `modura.config.ts`. This repository uses `file:contracts/releases`.

**Plain JSON files, not SQLite.** A SQLite file is binary, so a pull request cannot show what a release changed and git cannot merge two branches that both touched it. Every write also rewrites database pages, so each release adds another copy of the whole file to the history. One text file per release avoids all three problems. A release is about 28 KB, and git stores the next one as a delta.

**The format is the registry contract.** Each file holds exactly what `registry.getRelease` returns: `{ release: { summary, changes }, ir }`. `registry verify` checks files against a schema generated by compiling the registry module, not against a hand-written copy, and the SDK's generated types read them. Files are canonical JSON (keys sorted, two-space indentation, trailing newline), so they read like code in review. `irSha256` is still the hash of the compact canonical IR, so formatting never changes it.

**Names carry the number.** `000001.json`, `000002.json` and so on: six digits, so names sort in release order.

**Same rules, same messages.** Publishing to files runs the checks the Go registry runs, in the same order and with the same codes and messages: `INVALID_IR`, `NOTHING_TO_PUBLISH`, `INCOMPATIBLE_CHANGE`. The CLI writes the next file but does not commit it.

**Git does what the server does with locks.** Two branches that both publish create the same file name, so the second merge stops on an add/add conflict. That is `STALE_BASE` in git form, and the fix is the same: rebase, drop your file, publish again. No idempotency keys are needed, because rerunning a publish that already succeeded gives `NOTHING_TO_PUBLISH`. The publisher's identity is the commit author. `publishedBy` in the file comes from `MODURA_PUBLISHER` or `git config user.name` and is informational, and it never holds an email address.

**`registry verify` is the enforcement.** Every file is checked on its own: it is named like a release, numbers start at 1 with no gaps, it matches the registry schema, it is in canonical form (so no hand edits), the IR is valid, and the hash, IR version and module list match the IR. With `--since <git-ref>`, files that existed at that ref must be byte-identical and still present, and every file added since then must be exactly what `modura publish` would have written after its predecessor, including its recorded changes.

**Old releases are not judged again.** A later engine version may make the compatibility rules stricter. If `verify` re-checked the whole history, an old release could start failing even though it was valid when it was published. So a release is checked once, when it is added (`--since`), and its recorded `changes` stay as they were.

## What git does not give us

Rules enforced by CI are only as strong as the branch protection behind them. Anyone who can push to the default branch, or merge without the check, can rewrite the history. The server registry refuses a bad release whoever sends it. That is the honest difference between the two backends, and why both exist:

- **Files**: no service to run, history reviewed in pull requests, enforcement through a required CI check.
- **Server**: enforcement that does not depend on CI, plus readers at runtime (the MCP tools `registry_listReleases` and `registry_getRelease`).

## Alternatives considered

- **SQLite in the repository.** Rejected for the reasons above.
- **Git tags on commits that hold the IR.** Lighter, but a tag holds no summary or change list, tags are easy to move or delete, and pull requests do not review them.
- **One growing JSON file with every release.** Each publish would rewrite the file, and two branches would conflict on unrelated lines instead of on the release number.
- **Compressed release files.** A release is small and git compresses its objects already, and compression would make the files impossible to review.

## Consequences

- `pnpm modura publish` in this repository now writes a file. The demo and E2E still publish to the Go service by passing its URL.
- The release format is now a public format. Changing it means a new version of the registry module, which is the same rule the server already follows.
- `pnpm verify` runs `registry verify` and `compat --against registry`, and CI runs `registry verify --since origin/<base>` on pull requests.

## Evidence

- `packages/cli/src/file-registry.test.ts`: release 1 and its summary, refusals with the server's codes and messages, all 53 shared compatibility cases (the ones the Go registry passes), each kind of tampering, append-only checks against a real git repository, and the merge conflict between two branches. Turning off the append-only check or the recorded-changes check fails its test.
- `tests/e2e/registry.spec.ts`: the same contract published to the running Go registry and to a file registry gives the same summary (apart from `publishedAt` and `publishedBy`), changes and IR.
- `contracts/releases/000001.json`: this repository's first release.
